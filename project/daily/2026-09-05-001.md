Analyse détaillée & Adaptation au projet Orbis

# EntityDefinition
Le concept d'EntityDefinition répond directement à votre volonté de ne plus créer « une API par table » tout en posant une base solide.

Ce qui s'applique parfaitement à Orbis :
Referentiels vs Métier vs Authentification : La distinction faite dans votre note (codesnaf, codepostal, comptespcg vs entreprise, adresse) correspond exactement aux besoins d'Orbis. Les référentiels servent à alimenter les listes de choix (menus déroulants, boutons radio), tandis que les entités métiers représentent les nœuds de la hiérarchie à 4 couches.
Génération automatique côté Front (Uiport) : En transmettant l'EntityDefinition via l'API, le front-end JS / Uiport peut construire automatiquement le Store local, générer la recherche et valider les champs.

Ajustement nécessaire pour la hiérarchie à 4 couches :

Dans l'exemple fourni, la section fields est une liste à plat (['siren', 'raison_sociale', ...]). Pour supporter la structure à 4 couches d'Orbis, l'EntityDefinition doit inclure explicitement le bloc relations au niveau de l'entité, et pas uniquement dans la vue :

```php
'relations' => [
    'salaries'      => ['type' => 'hasMany', 'entity' => 'salarie'],
    'equipements'   => ['type' => 'hasMany', 'entity' => 'equipement'],
    'interventions' => ['type' => 'hasManyThrough', 'entity' => 'intervention', 'via' => 'equipement']
]
```


# ViewDefinition
ViewDefinition le pont direct vers Uiport
C'est ce concept qui résout le problème de l'évolution vers l'IHM et des composants adaptés (listes de choix, boutons radio, etc.).

1. Vue Selector (Ex: CodePostalSelector, SalarieSelector) :
Cas d'usage Orbis : Lorsqu'une intervention a lieu sur un équipement, l'IHM doit afficher un sélecteur de techniciens/salariés appartenant uniquement à l'entreprise concernée.
Rendu Uiport : Permet d'instancier un composant Select ou Autocomplete asynchrone qui ne charge que la clé primaire et le libellé (id, nom_prenom).

2. Vue Form avec types de composants UI (Ex: Radio vs Select) :
Pour que la ViewDefinition guide Uiport sur le bon composant, il est judicieux d'associer un widget aux champs dans la vue formulaire :

```php
[
    'name' => 'InterventionForm',
    'type' => 'form',
    'fields' => [
        'equipement_id' => ['widget' => 'select'],
        'type_priorite' => ['widget' => 'radio_group', 'options' => ['Basse', 'Moyenne', 'Haute']],
        'articles_utilises' => ['widget' => 'dynamic_array'] // Pour la GMAO / Stock
    ]
]
```
3. Vue Tree (Ex: OrganisationTree, ComptePcgTree) :
Cas d'usage Orbis : Parfaitement adapté pour visualiser l'arborescence à 4 couches : Entreprise ➔ Équipements ➔ Interventions.

C. Analyse critique de la partie api dans l'exemple
L'exemple propose une cartographie CRUD explicite par entité (/api/entreprise, /api/entreprise/{id}, etc.).
Limite pour Orbis : Conserver des routes purement REST par entité réintroduit l'approche « une API par table » si le front doit faire 4 requêtes successives pour afficher une intervention et ses consommables.
Recommandation :
Utiliser les routes REST simples de l'EntityDefinition pour les référentiels (codepostal, codesnaf), mais adosser des endpoints composites ou des vues API aux ViewDefinition pour les entités complexes :
Exemple : GET /api/entreprise/{id}/tree ou GET /api/equipement/{id}/intervention-builder.

3. Recommandation d'intégration dans la feuille de route
Adopter EntityDefinition dans Orbis (Python/SQLite) : Utiliser ce descripteur neutre comme contrat unique entre Orbis (moteur métier/tests) et CodeIgniter.
Exposer les ViewDefinition aux Controllers CodeIgniter : Les controllers CodeIgniter lisent les définitions de vues pour retourner la structure JSON attendue par Uiport.
Formaliser le composant ViewDefinition : Étant donné l'arrivée de Uiport et la complexité des formulaires (boutons radio, listes dépendantes), le concept de ViewDefinition mérite d'être documenté et implémenté comme un standard à part entière dans l'architecture Orbis/CodeIgniter.

1. Transposition directe des structures en JavaScript / TypeScript
En JS ou TS, une EntityDefinition et une ViewDefinition se traduisent par de simples objets littéraux ou des interfaces typées :

```js
// entityDefinitions/entreprise.js
export const EntrepriseEntity = {
  name: 'entreprise',
  label: 'Entreprise',
  description: 'Entreprise ou établissement',
  readonly: false,

  api: {
    list: '/api/entreprise',
    show: '/api/entreprise/:id',
    create: '/api/entreprise',
    update: '/api/entreprise/:id',
    delete: '/api/entreprise/:id'
  },

  fields: {
    siren: { type: 'string', required: true },
    raison_sociale: { type: 'string', required: true },
    naf_id: { type: 'number' },
    adresse_id: { type: 'number' }
  },

  relations: {
    salaries: { type: 'hasMany', entity: 'salarie' },
    equipements: { type: 'hasMany', entity: 'equipement' }
  }
};
```

2. Exploitation pratique dans le Front-End (Uiport / JS)
L'avantage majeur en JavaScript est que ce descripteur peut être consommé directement par vos composants IHM et vos stores.
A. Génération dynamique de formulaires dans Uiport
Au lieu de coder un formulaire en HTML/JS à la main, un composant générique lit la vue et génère les bons composants UI (champs texte, sélecteurs, boutons radio) :

```js
// Exemple de composant de rendu générique (ex: Uiport Form Render)
function renderView(viewDefinition, entityDefinition) {
  const form = document.createElement('form');

  viewDefinition.fields.forEach(fieldKey => {
    const fieldConfig = entityDefinition.fields[fieldKey];
    const widgetType = viewDefinition.widgets?.[fieldKey] || 'input-text';

    // Instanciation dynamique du composant Uiport
    const inputComponent = Uiport.createWidget(widgetType, {
      name: fieldKey,
      label: fieldConfig?.label || fieldKey,
      required: fieldConfig?.required
    });

    form.appendChild(inputComponent);
  });

  return form;
}
```

B. Génération automatique du Store JS
Vous pouvez créer un Store centralisé (Pinia, Redux, Zustand ou un store JS maison) de manière dynamique à partir du nom de l'entité :
```js
// storeFactory.js
export function createEntityStore(entityDefinition) {
  return {
    state: {
      items: [],
      selectedItem: null,
      loading: false
    },
    actions: {
      async fetchList() {
        this.state.loading = true;
        const res = await fetch(entityDefinition.api.list);
        this.state.items = await res.json();
        this.state.loading = false;
      },
      async getById(id) {
        const url = entityDefinition.api.show.replace(':id', id);
        const res = await fetch(url);
        this.state.selectedItem = await res.json();
      }
    }
  };
}

// Utilisation
const entrepriseStore = createEntityStore(EntrepriseEntity);
```

Voici comment consommer cet endpoint et manipuler la ViewDefinition et les données directement depuis la console de ton navigateur (F12) :
1. Script d'exécution (Console JS)
Ouvre la console de ton navigateur sur une page de ton domaine et exécute ce code :
```js
(async () => {
  try {
    // 1. Appels de l'API CodeIgniter
    const response = await fetch('/api/interventions/12');
    
    if (!response.ok) {
      throw new Error(`Erreur HTTP: ${response.status}`);
    }

    const payload = await response.json();

    // 2. Séparation de la métadonnée (ViewDefinition) et de la donnée
    const { meta, data } = payload;

    // 3. Inspection des objets dans la console
    console.group('📦 Réponse API Orbis / CodeIgniter');
    console.log('📐 ViewDefinition (meta) :', meta);
    console.log('📊 Données (data) :', data);
    console.groupEnd();

    // 4. Exemple de rendu dynamique très simple basé sur la ViewDefinition
    console.group('⚙️ Simulation de rendu Uiport');
    
    Object.entries(meta.fields).forEach(([fieldKey, config]) => {
      const value = data[fieldKey];

      // On simule le comportement selon le type de widget décrit dans la ViewDefinition
      switch (config.widget) {
        case 'data_table':
          console.log(`[TABLEAU] ${config.label} :`);
          console.table(value); // Affiche le tableau d'articles sous forme de tableau interactif
          break;

        case 'entity_card':
          console.log(`[CARTE RELATIVE] ${config.label} :`, value?.nom || value);
          break;

        case 'radio_group':
        case 'datepicker':
        case 'text':
        default:
          console.log(`[CHAMP ${config.widget.toUpperCase()}] ${config.label} :`, value);
          break;
      }
    });

    console.groupEnd();

  } catch (error) {
    console.error('❌ Erreur lors de la récupération :', error);
  }
})();
```
