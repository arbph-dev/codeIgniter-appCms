


Le contrat Panel (render / show / clear / destroy) est proprement tenu dans les deux panels. C'est ce qui permet au Workbench d'être un pur assembleur — aucune logique d'affichage ne s'y glisse, et ça se voit. La séparation est franche.

Le namespacing wb:mot:page sur le bus est une bonne discipline : quand plusieurs Workbenches cohabiteront, il n'y aura pas de collision. Idem pour les classes CSS wb_mot_*.

Le mix callbacks (panel → workbench) / bus (pagination → workbench) est cohérent : les callbacks restent locaux à l'instance, le bus ne sert qu'à ce qui traverse les frontières.

Ce qui mérite attention avant d'avancer sur le CRUD

destroy() appelle this.bus.unsubscribe?.('wb:mot:page') sans passer la référence du callback. Selon l'implémentation du bus, ça peut ne rien désabonner et laisser un listener zombie. À vérifier ou à corriger avant de multiplier les instances.

Le bug fetchMot sans q est documenté dans le code, ce qui est bien, mais il est aussi actif : la liste initiale ne pagine pas correctement. C'est un fix simple et il bloquera le CRUD dès qu'on voudra tester la pagination après un ajout. Autant le solder maintenant.

Ce qui peut attendre

WorkbenchBase.renderStructure() génère un .wb-header que le CSS de motWorkbench cache immédiatement avec display: none. Ce n'est pas grave en Step 1 mais ce sera à nettoyer quand le header aura un contenu réel.

Le stub CSS dans mot.php duplique des règles de workbench.css. C'est un choix de confort pour le développement, rien à redire pour l'instant.

En résumé

L'architecture tient la route et le rythme incrémental (Steps 1/2/3 documentés dans les commentaires) est une bonne façon de ne pas sur-ingénierer. Le seul vrai point de fragilité avant le CRUD c'est le unsubscribe — si les Workbenches peuvent s'ouvrir et se fermer plusieurs fois, ce leak peut devenir désagréable à debugger.

fetchMotLike — la version 002 est correcte mais le code de la 001 commentée devrait être supprimé plutôt que conservé. 
Le bus.publish commenté dans la 001 est révélateur d'une hésitation architecturale : le service a failli prendre en charge de l'UI. C'est bien que cette voie ait été abandonnée — le service ne doit pas connaître le bus.

Un point de fragilité : fetchMotLike avale silencieusement toutes les erreurs réseau (catch { return [] }). 
C'est un choix délibéré pour de l'autocomplétion — acceptable — mais si cette fonction est un jour réutilisée dans un contexte où l'erreur compte, ce comportement peut surprendre. Un commentaire explicite du choix serait utile.

saveMot est bien écrit, la bascule POST/PUT sur id est lisible. Le commentaire sur le 422 mérite d'être remonté dans MotWorkbench plutôt que dans le service : c'est le Workbench qui devra interpréter ce code et afficher un message utilisateur ("ce mot existe déjà"), pas le service qui doit juste propager l'erreur.

Ce qui veut dire que dans load() et dans le futur handler de sauvegarde, il faudra distinguer :

```js
catch (err) {
    if (err.message.includes('422')) {
        // feedback utilisateur "mot déjà existant"
    } else {
        this.listPanel.showError(err.message)
    }
}
```
