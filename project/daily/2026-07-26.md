## Points traités

### 1. Gestion du bus

**Avant (Iter004)**  
`WorkbenchBase` cherchait le bus dans `config.eventBus || window.bus || null`.  
Fragile : dépend de l'ordre de chargement des scripts et de globals.

**Après (Iter005)**  
```js
// WorkbenchBase.js
import { bus } from '/assets/js/core/eventBus.js';
// ...
this.bus = bus;   // singleton importé directement
```

Façade exposée aux classes filles :
```js
this.publish('cms:article:loaded', { slug });
this.subscribe('cms:section:change', (data) => { ... });
```

`window.eventBusPublish` (héritage bootstrap.js) n'est plus nécessaire.

---

### 2. Gestion des composants — suppression de bootstrap.js

**Avant (Iter004)**  
`setupComponentRegistry()` enregistrait une seule fonction `initCms`  
qui appelait `bootstrap.js/initCms()` — fichier d'essai, couplage fort.

**Après (Iter005)**  
Chaque composant est importé et enregistré individuellement :

```js
// CmsArticleWorkbench.js
import { initApex }    from '/assets/js/components/apex.js';
import { initCallout } from '/assets/js/components/callout.js';
import { initCodeVal } from '/assets/js/components/codeval.js';
import { initLeaflet } from '/assets/js/components/leaflet.js';
import { initMermaid } from '/assets/js/components/mermaid.js';
import { init as initThree } from '/assets/js/components/three/index.js';

setupComponentRegistry() {
    this.register('apex',    initApex);     // ① dépendance codeval
    this.register('callout', initCallout);  // ② indépendants
    this.register('leaflet', initLeaflet);
    this.register('mermaid', initMermaid);
    this.register('three',   initThree);
    this.register('codeval', initCodeVal);  // ③ consommateur d'events
}
```

`bootstrap.js` n'est plus importé.  
L'ordre apex → codeval est préservé (contrainte documentée dans bootstrap.js).

---

### 3. Intégration de domhelper

**Avant (Iter004)**  
`getElement()` utilisait `this.domHelper` (config externe optionnel) ou  
`this.container.querySelector()` brut.

**Après (Iter005)**  
```js
// WorkbenchBase.js
import { qs, qsa, byId, create, clear, toggle } from '/assets/js/core/domhelper.js';

// exposés aux classes filles via this.dom
this.dom = { qs, qsa, byId, create, clear, toggle };

// getElement() utilise qs importé
getElement(selector) {
    return qs(selector, this.container);
}
```

Prochaine étape : `templates.js` et `validation.js` selon le même pattern.

### 4. TabSystem — nouveau composant

**Fichier** : `assets/js/ui/workbench/TabSystem.js`
  https://github.com/arbph-dev/codeIgniter-appCms/blob/main/refactoring/assets/js/ui/workbench/TabSystem.js

Système d'onglets générique, indépendant du CMS.

#### API

| Méthode | Description |
|---------|-------------|
| `addTab(id, label, renderFn, initFn?)` | Ajoute un onglet. Chaînable. |
| `activate(id)` | Active un onglet. Init paresseuse (initFn une seule fois). |
| `render(container)` | Construit nav + panes. Active le premier onglet. |
| `updateTabContent(id, content)` | Met à jour un pane (HTMLElement ou string). |
| `setBadge(id, text)` | Ajoute un badge/compteur au bouton nav. |
| `destroy()` | Vide et libère. |

#### Exemple — sections d'article

```js
// Dans CmsArticleWorkbench (Iter006+)
loadSections(sections) {
    const tabs = this.initTabSystem();
    const container = this.getElement('#wb-content');

    sections.forEach(section => {
        tabs.addTab(
            `section-${section.id}`,
            section.title,
            () => {
                const div = this.dom.create('div', { class: 'cms_section' });
                div.innerHTML = section.content;
                return div;
            },
            (pane) => {
                // init composants de la section au premier affichage
                this.initRegisteredComponents();
            }
        );
    });

    tabs.render(container);
}
```

#### Carte des méthodes utiles pour le TabSystem

##### Méthodes clés — lecture

|Méthode|Retourne|Notes|
|---|---|---|
|`getPublishedArticle(slug)`|`?array`|Article seul, **sans sections**|
|`getSectionsByArticle(id)`|`array`|Sections d'un article, triées par position, `is_published = 1`|
|`getFullArticle(slug)`|`array`|Article + sections + parts (arbre complet)|
|`getArticleTree(slug)`|`array`|Article + sections **sans parts** — mais utilise `getArticle()` (pas de filtre `is_published`) ⚠|
|`renderSection(id)`|`string`|HTML fragment → parfait pour `fetchSection()`|
|`renderArticle(slug)`|`string`|HTML de toutes les sections — utilisé en mode plat|
|`getSectionsByArticle()`|`array`|= ce que j'ai appelé `getArticleSections()` en Iter006.1|

---

#### Flux de données — mode tabs vs mode plat

```
CmsController::article($slug)
  │
  ├─ getPublishedArticle($slug)           → $article (sans sections)
  ├─ getSectionsByArticle($article['id']) → $article['sections']   ← AJOUT Iter006.1
  └─ renderArticle($slug)                 → $content  (HTML complet, fallback mode plat)
        └─ getFullArticle()               (recharge article + sections + parts)
              └─ getSectionsByArticle()
              └─ getPartsBySection() × N
```

**Observation :** `renderArticle()` recharge l'article via `getFullArticle()`. Il y a donc une double lecture en mode tabs (article lu deux fois). Acceptable pour l'instant — à optimiser si besoin via un cache ou en passant l'objet.

---

#### Ce que le JS reçoit dans `article.sections`

`getSectionsByArticle()` retourne pour chaque section les colonnes de la table, soit au minimum :

```js
article.sections = [
    { id: 1, article_id: 5, slug: 'intro',   title: 'Introduction',  position: 1, is_published: 1 },
    { id: 2, article_id: 5, slug: 'dev',     title: 'Développement', position: 2, is_published: 1 },
    { id: 3, article_id: 5, slug: 'conclusion', title: 'Conclusion', position: 3, is_published: 1 },
]
```

Le `TabSystem` n'a besoin que de `id`, `title`, `position` → c'est exactement ce qu'il reçoit. Les `parts` ne sont **pas** incluses ici, contrairement à `getFullArticle()` — c'est voulu : on ne charge les parts que quand l'onglet est activé (via `fetchSection()`).

#### `renderSection()` — compatibilité avec `fetchSection()`

```php
public function renderSection(int $sectionId): string
{
    $section = $this->sections->find($sectionId);
    if (!$section) { return ''; }
    return $this->renderSectionData($section, $this->getPartsBySection($sectionId));
}

private function renderSectionData(array $section, array $parts): string
{
    $html = '';
    foreach ($parts as $part) {
        $html .= $this->renderPart($part);  // view('cms/part', ...)
    }
    return view('cms/section', ['section' => $section, 'content' => $html]);
}
```

`renderSection()` retourne le résultat de `view('cms/section', ...)` — un **fragment HTML** sans `<html>/<head>`. ✅ C'est exactement ce que `fetchSection()` attend pour l'injection.

#### 3 Points de vigilance — rappel

##### [1] Collision slug dans `section.php`

```html
<section id="<?= esc($section['slug'] ?? ('section-' . $section['id'])) ?>">
```

Si deux articles partagent un slug de section identique (ex: `introduction`), deux éléments avec le même `id` HTML coexisteront dans la page. **Règle** : prefixer les slugs par l'article → `test-art-introduction`, pas `introduction`. Le seed SQL applique déjà cette convention.

##### [2] Triple lecture DB en mode tabs

```
getPublishedArticle()      → article row (lecture 1)
getSectionsByArticle()     → sections[]  (lecture 2)
renderArticle()            → getFullArticle() = article + sections + parts (lecture 3)
```

`$content` (résultat de lecture 3) n'est pas utilisé en mode tabs. **Optimisation future** : ne pas appeler `renderArticle()` si `count($article['sections']) > 1`. Prématuré — le fallback mode plat justifie les 3 lectures pour l'instant.

##### [3] `initRegisteredComponents()` — scope global

Appelé après chaque `fetchSection()`, il scanne `document` entier. Un composant déjà rendu dans un pane précédent peut être ré-initialisé. **Résolution : Iter007** — `initXxx(root = document)` avec root = pane courant.

##### Refactoring prévu : `initXxx(root = document)`

**Principe** : chaque fonction d'init reçoit un paramètre `root` optionnel. Elle scanne `root.querySelectorAll(...)` au lieu de `document.querySelectorAll(...)`. Compatibilité descendante maintenue — `root` vaut `document` si non fourni.

```js
// Avant
export function initCallout() {
    document.querySelectorAll('[data-callout]').forEach(el => { … });
}

// Après
export function initCallout(root = document) {
    root.querySelectorAll('[data-callout]').forEach(el => { … });
}
```

**Côté WorkbenchBase** — nouvelle méthode :

```js
initRegisteredComponentsIn(rootElement) {
    for (const [name, initFn] of this.componentRegistry) {
        try {
            initFn(rootElement);   // ciblé sur le pane
        } catch (e) {
            console.error(`[Workbench] Erreur init "${name}" dans root`, e);
        }
    }
}
```

**Côté CmsArticleWorkbench.fetchSection()** :

```js
// Remplace this.initRegisteredComponents()
this.initRegisteredComponentsIn(paneEl);
```
