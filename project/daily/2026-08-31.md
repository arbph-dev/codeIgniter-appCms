     * Construit la ligne 4 formatée de l'adresse.
     * Ex : "125 Bis RUE des Lilas"
     */
    public static function formatLigne4(array $row): string
    {
        return trim(implode(' ', array_filter([
            $row['voienumero']   ?? null,
            self::rptLabel($row['voierpt'] ?? null),
            $row['voietype_nom'] ?? null,
            self::charniereLabel(isset($row['voiecharniere']) ? (int)$row['voiecharniere'] : null),
            $row['voienom']      ?? null,
        ])));
    }

Ce qui a changé et pourquoi
withRelations() — les 4 joins au lieu de 2

Le problème central : adresses ne stocke pas une ligne4 textuelle, elle stocke des champs normalisés que AdresseModel::formatLigne4() assemble en PHP. Il faut donc remonter les tables liées :

etablissements → adresses → type_voies     (pour voietype_nom)
                           → codes_postaux  (pour cp_codepostal, cp_commune)

Les 5 champs sélectionnés (voienumero, voierpt, voiecharniere, voienom, voietype_nom) sont exactement ce que formatLigne4 consomme. Un seul point à vérifier dans ton schéma : les FK s'appellent-elles bien adresses.voietype_id et adresses.code_postal_id ? Ajuste les deux ->join() si c'est différent.

Pattern enrich / enrichAll (statics sur le model)

Plutôt que de dupliquer la logique dans chaque méthode, deux statics propres :

enrich($row) → ajoute ligne4 via AdresseModel::formatLigne4()
enrichAll($rows) → array_map sur le tableau paginé

Le controller appelle toujours l'un ou l'autre après chaque find() — sauf suggest() qui ne sélectionne pas les champs d'adresse, donc pas d'enrich là.

siege() — refetch après le service

EntrepriseService::ensureSiege() retourne un find() nu (sans joins). Le controller refetch maintenant avec withRelations() avant d'enrichir, donc la réponse JSON contient bien ligne4, cp_codepostal, cp_commune comme les autres endpoints.
