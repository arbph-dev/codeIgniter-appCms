e conserverais ta convention `image_mot`, mais je ferais une petite amélioration au pivot : **ajouter les clés étrangères et un ordre cohérent `image_id, mot_id`**, puisque notre point d'entrée principal sera l'ImageTagger.

## 1. Migration du pivot

Je partirais sur une table strictement minimale, sans timestamps : la date de création de la relation n'est pas encore une donnée métier.

```
<?php

namespace App\Database\Migrations;

use CodeIgniter\Database\Migration;

class CreateImageMotTable extends Migration
{
    public function up()
    {
        $this->forge->addField([
            'image_id' => [
                'type'       => 'INT',
                'constraint' => 10,
                'unsigned'   => true,
            ],
            'mot_id' => [
                'type'       => 'INT',
                'constraint' => 10,
                'unsigned'   => true,
            ],
        ]);

        $this->forge->addKey(['image_id', 'mot_id'], true);
        $this->forge->addKey('mot_id');

        $this->forge->addForeignKey(
            'image_id',
            'images',
            'id',
            'CASCADE',
            'CASCADE'
        );

        $this->forge->addForeignKey(
            'mot_id',
            'mots',
            'mot_id',
            'CASCADE',
            'CASCADE'
        );

        $this->forge->createTable('image_mot');
    }

    public function down()
    {
        $this->forge->dropTable('image_mot', true);
    }
}
```

Le point important est le second index :

```
$this->forge->addKey('mot_id');
```

La PK :

```
(image_id, mot_id)
```

optimise :

```
GET /api/image/:id/mots
```

et l'index sur `mot_id` optimise l'autre sens :

```
GET /api/mot/:id/images
```

# 2. `ImageMotModel`

Je créerais un modèle dédié au pivot, mais **sans lui donner de logique métier**.

```
<?php

namespace App\Models;

use CodeIgniter\Model;

class ImageMotModel extends Model
{
    protected $table      = 'image_mot';
    protected $primaryKey = 'image_id';

    protected $allowedFields = [
        'image_id',
        'mot_id',
    ];

    protected $returnType = 'array';

    protected $useTimestamps = false;
}
```

Cependant, il y a un détail important : **`image_id` n'est pas réellement une PK individuelle**. La clé est composée de :

```
(image_id, mot_id)
```

CodeIgniter Model n'est donc pas idéal pour représenter ce pivot comme un CRUD classique.

Je recommande plutôt de considérer `ImageMotModel` comme un **repository/query model de pivot**, et de ne jamais utiliser :

```
find($id)
update($id)
delete($id)
```

sur ce modèle.

Les opérations seront explicitement faites avec :

```
where('image_id', ...)
where('mot_id', ...)
```

C'est plus fidèle au modèle relationnel.

            ->findAll();

    }

    public function detach(int $imageId, int $motId): bool
    {
        // suppression de la relation uniquement
    }

    public function sync(int $imageId, array $motIds): array
    {
        // synchronisation transactionnelle
    }
}

Oui. Avec les clés étrangères correspondant exactement à tes deux modèles (`images.id` et `mots.mot_id`), je recommande :

```
CREATE TABLE image_mot (
    image_id INT UNSIGNED NOT NULL,
    mot_id   INT UNSIGNED NOT NULL,

    PRIMARY KEY (image_id, mot_id),

    INDEX idx_image_mot_mot_id (mot_id),

    CONSTRAINT fk_image_mot_image
        FOREIGN KEY (image_id)
        REFERENCES images (id)
        ON DELETE CASCADE
        ON UPDATE CASCADE,

    CONSTRAINT fk_image_mot_mot
        FOREIGN KEY (mot_id)
        REFERENCES mots (mot_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
) ENGINE=InnoDB;
```

### Pourquoi cette structure

- `PRIMARY KEY (image_id, mot_id)` interdit automatiquement les doublons.
- `INDEX ... (mot_id)` optimise le parcours inverse :  
    `GET /api/mot/:id/images`.
- `ON DELETE CASCADE` supprime automatiquement les associations lorsqu'une image ou un mot est supprimé.
- **Pas de `created_at` / `updated_at`** : la table représente ici une association pure, sans attribut métier.

On obtient donc :

```
images
  id
   │
   │
   ▼
image_mot
 ┌──────────┬────────┐
 │ image_id │ mot_id │
 ├──────────┼────────┤
 │    17    │   3    │
 │    17    │   8    │
 │    21    │   3    │
 └──────────┴────────┘
              │
              ▼
             mots
           mot_id
```

Cette structure est suffisante pour commencer `Image ↔ Mot` et préparer le `ImageTaggerWorkbench`
