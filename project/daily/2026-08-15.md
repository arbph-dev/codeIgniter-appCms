# bloc Relation
Model + Entity

Deux différences clés par rapport à parcours_types qui orientent le code :

source_type et target_type sont des ENUM NOT NULL indexés 
— c'est le filtre principal de ce référentiel. symetrique est un tinyint(1) NOT NULL DEFAULT 0 — cast boolean. inverse_code est nullable — auto-référence vers un autre code de la même table.


Divergence ENUM entre les deux tables :
- relation_types  enum('personne','organisation','etablissement')
- relations   enum('personne','organisation')

etablissement peut être défini dans le référentiel mais ne peut pas être utilisé dans une relation réelle. La base est source de vérité 
— on code ce qui existe, et on signale la décision à prendre : 

étendre l'ENUM de relations ou retirer etablissement de relation_types. Ce choix est le vôtre, pas une correction de code.

Le reste est propre : actif est tinyint(1) DEFAULT 1 — boolean vrai avec défaut actif. ordre est smallint DEFAULT 0. Les dates métier vont dans $dates.

2 fichiers créés, lu un fichier

## Entity 
— date_debut et date_fin dans $dates comme demandé.
CodeIgniter les hydratera en objets Time à la lecture, ce qui permettra les comparaisons temporelles dans le service sans conversion manuelle.

## Model 
trois méthodes, une philosophie : le modèle ne fait que des requêtes, pas de logique métier.

- findForEntity() est la requête symétrique
    elle remonte toutes les relations d'une entité qu'elle soit source ou cible. C'est le cas d'usage de la fiche personne. Elle filtre actif = 1 par défaut et trie par ordre puis date_debut.
- findBySource() et findByTarget() couvrent les cas orientés
    utiles quand le service devra construire le graphe de relations dans un sens précis.

La constante ENTITY_TYPES est volontairement différente de RelationTypeModel::ENTITY_TYPES avec un commentaire TODO explicite — la divergence est documentée dans le code, pas masquée.

**Décision ENUM**
choix : option A
Une Personne peut etre lié à l'organisation `Leclerc`.
Si l'organisation `Leclerc` à des `etablissement` on proposerait la liste. Si l'information `etablissement` est disponible on gère `etablissement` en relation sinon on reste sur `organisation`

```sql
-- Option A RETENUE — étendre relations (recommandé si établissements doivent être liés)
ALTER TABLE relations 
    MODIFY source_type ENUM('personne','organisation','etablissement') NOT NULL,
    MODIFY target_type ENUM('personne','organisation','etablissement') NOT NULL;
-- Option B — restreindre relation_types (si établissement n'est jamais une entité relationnelle)
ALTER TABLE relation_types
    MODIFY source_type ENUM('personne','organisation') NOT NULL,
    MODIFY target_type ENUM('personne','organisation') NOT NULL;
```

## RelationService
App/Services/RelationService;

### applyTargetResolution()
Règle métier.
- Le payload d'entrée accepte un etablissement_id optionnel. Si présent avec une cible organisation, il bascule silencieusement vers etablissement. 
- Le champ est consommé avant l'INSERT — la base ne le voit jamais. Le front peut donc toujours envoyer target_type=organisation + etablissement_id=7 sans avoir à décider lui-même.

### validateRelationType()
Garde-fou entre le référentiel et les données réelles.
Un type employe défini pour personne→organisation ne peut pas être utilisé pour personne→personne.

La validation est explicite dans les logs si elle échoue, ce qui facilitera le debug.

### enrich()
Evite le N+1 : une Relation seule ne sert à rien sans savoir ce qu'est son relation_type_id.
- L'enrichissement est systématique dans toutes les méthodes publiques de lecture.

### deactivate()
complément à delete().
- Une relation historique (ancienne employée de Leclerc) n'a pas à être effacée, juste désactivée. actif=0 + date_fin raconte l'histoire.
