# Travaux
Bilan des ajouts

TabSystem iter007 — onTabChange(fn) est la pièce centrale : OrganisationWorkbench l'utilisera pour charger les adresses uniquement quand l'onglet "Adresses" est activé. resetTab(id) force le rechargement après un save sans détruire le TabSystem. markDirty/clearDirty sont prêts mais optionnels pour le premier OrganisationWorkbench.

Form.js v4 — radio et checkbox suivent exactement le même schéma que les types précédents. Le cas :has(input:checked) en CSS donne un retour visuel immédiat sur le radio sélectionné sans une ligne de JS supplémentaire.



Clair. Pas d'enum, pas de model — c'est un référentiel table pure. Deux conséquences directes.

1. Constantes JS miroir de la table

Les choix sont stables (7 types métier bien définis), on les hardcode dans un fichier constants. Si la table évolue un jour, un seul fichier à mettre à jour.

javascript
// assets/js/features/organisation/organisation.constants.js

export const ORGANISATION_TYPES = [
    { value: '1', label: 'Entreprise'              },
    { value: '2', label: 'Association loi 1901'    },
    { value: '3', label: 'Coopérative'             },
    { value: '4', label: 'Établissement public'    },
    { value: '5', label: 'Établissement scolaire'  },
    { value: '6', label: 'Collectivité territoriale'},
    { value: '7', label: 'Musée / Site culturel'   },
]

2. UX — radio ou select ?

7 choix en radio avec flex-wrap donnent 3-4 lignes — correct pour un formulaire de création. Mais en onglet compact (TabSystem), le select est plus sobre. 

Je propose **radio** pour la vue form principale, avec un type: 'select' en fallback si l'espace manque.

javascript
// Dans organisation.properties.js
{
    name        : 'organisation_type_id',
    description : 'Type',
    type        : 'radio',
    default     : '1',
    options     : {
        required : '',
        choices  : ORGANISATION_TYPES,
    },
}

Pour démarrer OrganisationWorkbench il me manque encore :

Api/Organisation.php   — format exact des réponses
                         GET  /api/organisation      → { data:[], pager:{} }
                         GET  /api/organisation/{id} → { data:{} }
                         POST /api/organisation      → { data:{} } ou { status, id }
                         PUT  /api/organisation/{id} → idem

Schema relation        — organisations ↔ adresses
                         table pivot ? ou adresse_id directe sur organisations ?


Tout ce qu'il faut. Structure claire, service déjà propre, schema complet. Je note les deux points d'architecture avant de coder.

Relations directes sur organisations :

adresse_id — FK directe (pas pivot) → AdressePickerDialog = RelationPickerDialog configuré avec fetchAdresseLike
withRelations() ne joint pas les adresses → displayFn affiche Adresse #id au chargement, itemDisplay donne le formatage complet après sélection picker. Backend à enrichir plus tard.

TabSystem dans OrgDetailPanel :

renderFn() → form.render() (construit le DOM)
initFn() → form.fill(org) (remplit au premier activate, lazy mais instantané — pas de fetch)

Décisions architecturales notables

_makeForm() dans OrgDetailPanel — une seule factory qui crée les trois Forms avec le même onSubmit → onSave(id, data). Chaque onglet sauvegarde indépendamment ses champs. Le backend CI n'applique que les allowedFields présents — envoyer des champs partiels est sûr.

AdressePickerDialog — pas un fichier séparé. C'est RelationPickerDialog configuré avec fetchAdresseLike et les colonnes adresse. L'abstraction RelationPickerDialog absorbe ce cas sans extension.

OrgListPanel.onPage(fn) — pagination via callback pur, cohérent avec le contrat panel. Le bus local wb:org:page est éliminé.

Point de vigilance avant test

OrgDetailPanel appelle this.listPanel.onPage dans _bindEvents() mais OrgListPanel utilise encore pagination({ busEvent: 'wb:org:page' }) 
il faut : 
- soit câbler le bus dans le Workbench
- soit modifier OrgListPanel.show() pour utiliser onPage via callback.

C'est l'incohérence de pagination identifiée en bilan AdresseWorkbench 
à corriger dans cette implémentation ou notée pour la prochaine session.
