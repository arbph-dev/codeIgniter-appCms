## Plan session
Ce qui est acquis depuis image.service.js
- fetchImage({ id, q, status, page, perPage })
- saveImage({ id, file, alt, status, user_id })   ← CREATE FormData / UPDATE JSON
- deleteImage(id)

Différences structurelles vs MotWorkbench

Deux modes de formulaire distincts :
- CREATE → file (upload) + alt + status
- UPDATE → alt + status seulement (PUT JSON)

Champs en lecture seule (calculés à l'upload, jamais éditables) : filename, width, height, ratio, extension, size_ko, path

**Form.js** doit être étendu pour supporter :

type: 'file' → input file
type: 'select' → select avec options (pour status)

Un pattern backend minimal et réplicable pour chaque Workbench de test :

```
Route    /workbench/{name}  →  WorkbenchController::{method}()
         Un seul contrôleur pour tous les workbenches de dev
         Une seule méthode par workbench
         Une vue qui est un stub pur — juste le div + le module JS
```

**Le "talonner" évité** — sans ce pattern on risquait de dupliquer des contrôleurs pour chaque Workbench, ou pire, de mélanger les routes dev avec les routes métier.

**Un groupe `workbench` isolé, un seul `WorkbenchController`, c'est propre et extensible.**

## Frontend

### API publique de Form.js

Quatre méthodes publiques, une seule responsabilité chacune.

---

**`render()`** construit le DOM du formulaire et le retourne. À appeler une fois, le résultat est appendé dans le Panel. Crée les champs depuis le PropertySet, les boutons, et branche les écouteurs Enter / Escape. Retourne l'élément racine `div.wb_form`.

**`fill(data)`** pré-remplit les champs avec un objet existant — c'est le mode édition. Gère la conversion `Date → YYYY-MM-DD` pour les champs de type `date`. Focus sur le premier champ + sélection du contenu pour édition rapide.

**`reset()`** remet tous les champs à leur `default` — c'est le mode création. Efface les erreurs inline. Focus sur le premier champ.

**`extract()`** est le moteur. Valide chaque champ via `_checkField()` (validation native navigateur puis `validate()` custom), affiche toutes les erreurs inline en une passe, donne le focus au premier champ invalide. Si tout est valide : caste les valeurs par type (`text | number | date`), calcule les `ComputePropertySet`, appelle `onSubmit(data)`. Retourne `null` si invalide, l'objet de données sinon.

---

Ce que le Panel fait autour de ces quatre méthodes : le verrou `_working` avant `onSubmit`, le feedback API (`showFeedback('error', '422...')`), l'affichage de l'ID en lecture seule. Form.js ne voit rien de tout ça — la frontière est nette.
