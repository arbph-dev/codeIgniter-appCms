Un pattern backend minimal et réplicable pour chaque Workbench de test :

```
Route    /workbench/{name}  →  WorkbenchController::{method}()
         Un seul contrôleur pour tous les workbenches de dev
         Une seule méthode par workbench
         Une vue qui est un stub pur — juste le div + le module JS
```

**Le "talonner" évité** — sans ce pattern on risquait de dupliquer des contrôleurs pour chaque Workbench, ou pire, de mélanger les routes dev avec les routes métier.

**Un groupe `workbench` isolé, un seul `WorkbenchController`, c'est propre et extensible.**

## Frontend

### API publique de Form.js

Quatre méthodes publiques, une seule responsabilité chacune.

---

**`render()`** construit le DOM du formulaire et le retourne. À appeler une fois, le résultat est appendé dans le Panel. Crée les champs depuis le PropertySet, les boutons, et branche les écouteurs Enter / Escape. Retourne l'élément racine `div.wb_form`.

**`fill(data)`** pré-remplit les champs avec un objet existant — c'est le mode édition. Gère la conversion `Date → YYYY-MM-DD` pour les champs de type `date`. Focus sur le premier champ + sélection du contenu pour édition rapide.

**`reset()`** remet tous les champs à leur `default` — c'est le mode création. Efface les erreurs inline. Focus sur le premier champ.

**`extract()`** est le moteur. Valide chaque champ via `_checkField()` (validation native navigateur puis `validate()` custom), affiche toutes les erreurs inline en une passe, donne le focus au premier champ invalide. Si tout est valide : caste les valeurs par type (`text | number | date`), calcule les `ComputePropertySet`, appelle `onSubmit(data)`. Retourne `null` si invalide, l'objet de données sinon.

---

Ce que le Panel fait autour de ces quatre méthodes : le verrou `_working` avant `onSubmit`, le feedback API (`showFeedback('error', '422...')`), l'affichage de l'ID en lecture seule. Form.js ne voit rien de tout ça — la frontière est nette.

---

### Form.js

Les 4 méthodes publiques suffisent à définir le contrat de Form.js.

```
Form
 ├── render()
 ├── fill(data)
 ├── reset()
 └── extract()
```


### render()
Construire le DOM du formulaire.
- crée les champs à partir du PropertySet ;
- crée les boutons ;
- branche les événements Enter / Escape ;
- mémorise les références des champs.

Il ne fait aucune validation. Il ne remplit aucune donnée.

Il retourne uniquement
```
<div class="wb_form">
```

### fill(data)
passe le formulaire en mode édition.

Son role :
- affecter les valeurs ;
- convertir Date → YYYY-MM-DD ;
- mettre le focus sur le premier champ éditable ;
- sélectionner le contenu.

Aucune validation.Aucun submit.

### reset()
préparer un nouveau formulaire.

Son role :
- remet les valeurs par défaut ;
- vide les erreurs ;
- vide les feedbacks internes ;
- focus premier champ.

Il ne connaît rien de l'API.

### extract()
Il produit un objet métier.

```
lecture
      ↓
validation HTML
      ↓
validation custom
      ↓
cast des types
      ↓
ComputePropertySet
      ↓
objet final
```

Retour :
```
null
```
ou
```
{
    alt,
    status,
    file,
    ...
}
```



Le Panel décide ensuite :
```
const data = form.extract();

if (!data) return;

await saveImage(data);
```

Form ne fait jamais de fetch().

Ce que Form ne doit jamais connaître
les Workbench ;
les Panels ;
l'API ;
les services ;
les messages de succès ;
les erreurs HTTP ;
_working ;
showFeedback().

Ces responsabilités restent dans ImageDetailPanel, exactement comme dans MotDetailPanel.

### Les méthodes privées

Je les laisserais volontairement non spécifiées.

Aujourd'hui elles seront probablement quelque chose comme :
```
_createField()

_createButtons()

_fillField()

_extractField()

_checkField()

_castValue()

_focusFirst()

_clearErrors()

_showFieldError()
```


Le vrai contrat de Form.js est simplement :
```
const form = new Form(propertySet);

panel.appendChild(form.render());

form.fill(image);      // édition

form.reset();          // création

const data = form.extract();

if (data)
{
    saveImage(data);
}
```


Un point d'arrêt pour la conception. Ce contrat est suffisamment petit pour rester stable, tout en étant assez riche pour couvrir MotWorkbench, ImageWorkbench, puis ComponentCatalogWorkbench. 

Les méthodes privées pourront être introduites lorsque l'implémentation fera apparaître des duplications réelles, plutôt que par anticipation.

---

En gardant extract() publique, on conserve une API plus générale et plus réutilisable. Cela laisse le choix au consommateur du formulaire.

Par exemple, les deux usages suivants restent possibles.

Mode autonome (comme aujourd'hui) :
```js
const form = new Form({
    propertySet,
    onSubmit: (data) => {
        save(data);
    }
});
```
Le bouton Enregistrer appelle extract() en interne puis déclenche onSubmit(data).

Mode piloté par le Panel :
```js
saveBtn.addEventListener('click', () =>
{
    const data = form.extract();
    if (!data) return;
    save(data);
});
```
Ce second mode pourra être utile dans des Workbench plus complexes (ComponentCatalogWorkbench, SceneWorkbench, ImageTaggerWorkbench...) où plusieurs formulaires, validations croisées ou assistants ("wizard") devront être coordonnés.
