## Contrat UI / Logique — proposition pour ORBIS

J'ai regardé l'ensemble des fichiers fournis (pas besoin d'aller chercher sur GitHub, le contenu est bien celui du projet). Voici mon diagnostic puis une proposition de contrat concrète.

### 1. Ce qui existe déjà et qui va dans le bon sens

Le projet a déjà une séparation en couches assez saine côté **données** :

- **Couche 2** (`acquisition/sources.py`) : dataclasses `from_api()` qui aplatissent les réponses brutes.
- **Couche 3** (`transformation/mapper.py`) : `EntrepriseMapper` qui transforme les sources en `EntrepriseModel`.
- **Couche 4** (`persistence/*`) : ORM + `SirenGuard` + `ConflictLog`, complètement indépendants de toute UI.
- Les `services/api/*_client.py` sont propres : ils retournent des `dict`/`None`, ne font aucun `print` métier (juste un log technique dans `BaseApiClient._request`).

Le problème n'est donc **pas** la donnée, c'est la couche « présentation/orchestration » (`cli/menus/*.py` et surtout `cli/layer5/etapes.py`) qui mélange trois responsabilités dans les mêmes fonctions :

1. **Saisie** (`Prompt.ask`, `Confirm.ask`, `IntPrompt.ask`)
2. **Décision métier** (quel candidat choisir, faut-il enrichir, faut-il persister…)
3. **Affichage** (`console.print`, `Table`, `Panel`)

`etapes.py` est le cas le plus grave : `_run_etape2` par exemple a `console.print` intercalés entre chaque décision (fallback Lucene, enrichissement SIRET, scoring). Impossible de rejouer cette logique depuis Qt sans dupliquer entièrement la fonction.

### 2. Le contrat proposé : Ports & Adapters

L'idée : **aucun module métier n'appelle plus jamais Rich directement**. À la place, il reçoit un port abstrait.

python

```python
# core/ui_port.py
from __future__ import annotations
from typing import Protocol, Optional, Sequence, Any

class UIPort(Protocol):
    """Contrat unique implémenté par RichUIPort (CLI) puis QtUIPort (wui.py)."""

    # ── Saisie ──────────────────────────────────────────
    def ask_text(self, label: str, default: str = "") -> str: ...
    def ask_int(self, label: str, default: int) -> int: ...
    def ask_choice(self, label: str, choices: Sequence[str], default: str | None = None) -> str: ...
    def ask_confirm(self, label: str, default: bool = False) -> bool: ...

    # ── Sortie ──────────────────────────────────────────
    def notify(self, message: str, level: str = "info") -> None: ...   # info/warn/error/success
    def show_table(self, title: str, columns: Sequence[str], rows: Sequence[dict]) -> None: ...
    def show_detail(self, data: Any) -> None: ...

    # ── Progression (utile pour étapes longues type layer5) ─
    def progress(self, current: int, total: int, label: str = "") -> None: ...
```

`RichUIPort` (aujourd'hui) :

python

```python
# cli/rich_ui_port.py
from rich.console import Console
from rich.prompt import Prompt, IntPrompt, Confirm
from rich.table import Table

class RichUIPort:
    def __init__(self):
        self.console = Console()

    def ask_text(self, label, default=""):
        return Prompt.ask(label, default=default)

    def ask_int(self, label, default):
        return IntPrompt.ask(label, default=default)

    def ask_choice(self, label, choices, default=None):
        return Prompt.ask(label, choices=list(choices), default=default)

    def ask_confirm(self, label, default=False):
        return Confirm.ask(label, default=default)

    def notify(self, message, level="info"):
        colors = {"info": "dim", "warn": "yellow", "error": "red", "success": "green"}
        self.console.print(f"[{colors.get(level,'dim')}]{message}[/]")

    def show_table(self, title, columns, rows):
        t = Table(title=title, show_lines=True)
        for c in columns:
            t.add_column(c)
        for r in rows:
            t.add_row(*[str(r.get(c, "")) for c in columns])
        self.console.print(t)

    def show_detail(self, data):
        from cli.presentation import json_tree
        self.console.print(json_tree(data))

    def progress(self, current, total, label=""):
        self.console.print(f"[dim]{label} {current}/{total}[/]")
```

Demain, `QtUIPort` implémente le **même contrat** avec des `QInputDialog`, `QTableWidget`, `QProgressBar` dans `wui.py` — et **aucune ligne de logique métier ne change**.

### 3. Les services métier retournent des DTO, jamais des `console.print`

Exemple avec `etape1_scan`, qui est aujourd'hui ~70 lignes mêlant tout :

python

```python
# core/services/layer5_service.py
from dataclasses import dataclass

@dataclass
class ScanResult:
    orphans: list[WMRecord]
    scanned: int
    page: int
    per_page: int
    to_enrich: int
    ratio_pct: float

class Layer5Service:
    def __init__(self, org_client: OrganisationClient, ent_client: EntrepriseClient):
        self.org_client = org_client
        self.ent_client = ent_client

    def scan_orphans(self, page: int, per_page: int) -> ScanResult:
        data = self.org_client.list(type_id=1, page=page, per_page=per_page)
        if not data:
            return ScanResult([], 0, page, per_page, 0, 0.0)

        orgs = data.get("data") or []
        linked_org_ids = self._index_linked_org_ids()

        orphans = [
            WMRecord(organisation_id=z.id, nom=z.nom or "", siren=z.siren,
                      type_id=z.organisation_type_id or 0, type_label=z.type_label,
                      status="orphan", zealot=z)
            for org in orgs
            if (z := OrganisationZealot.from_api(org)).organisation_type_id in TYPES_REQUIRING_ENTREPRISE
            and z.id not in linked_org_ids
        ]

        WorkingMemory.set_scan(orphans, scanned=len(orgs), page=page, per_page=per_page)
        st = WorkingMemory.stats
        return ScanResult(orphans, st["scanned"], page, per_page, st["to_enrich"], st["ratio_pct"])
```

Et le menu (`cli/menus/layer5.py`) devient un **pur présentateur**, qui pose les questions via le port puis affiche le résultat :

python

```python
def _do_etape1(service: Layer5Service, ui: UIPort):
    page = ui.ask_int("Page", default=1)
    per_page = ui.ask_int("Taille page", default=20)

    result = service.scan_orphans(page, per_page)

    ui.notify(f"{result.scanned} org(s) scannée(s) — {result.to_enrich} à enrichir ({result.ratio_pct} %)")
    if not result.orphans:
        ui.notify("Aucune orpheline sur cette page.", level="success")
        return

    ui.show_table("Orphelines", ["organisation_id", "nom", "siren", "type_label"],
                   [dataclasses.asdict(r) for r in result.orphans])
```

Ce même `Layer5Service.scan_orphans()` sera appelé **tel quel** depuis `wui.py`, seul le bloc `_do_etape1` change de forme (slots Qt au lieu de `Prompt.ask`).

### 4. Regrouper les clients API par domaine métier

Vous avez raison : `organisation`, `entreprise`, `etablissement`, `insee` sont aujourd'hui 4 clients HTTP séparés, mais consommés ensemble dans presque tous les workflows (voir `etapes.py`, `_lier_adresse_ban`, etc.). Je propose une **façade de domaine** au-dessus des clients HTTP, sans les fusionner (ils restent des clients HTTP purs et testables séparément) :

python


Ça correspond à ce que fait déjà `etape3_qualify_and_save`/`etape4_push_zealot`, mais actuellement noyé dans du Rich. En l'isolant, ce cas d'usage devient réutilisable (CLI, GUI, script batch, futur endpoint web).

### 5. Structure cible proposée

```
core/
  ui_port.py                  # Protocol UIPort
  services/
    layer5_service.py         # ScanResult, SearchResult, QualifyResult, PushResult
    entreprise_domain.py      # façade organisation+entreprise+etablissement+insee
    adresse_domain.py         # façade BAN + adresse + codepostal + typevoie

  rich_ui_port.py             # implémentation Rich du UIPort
  menus/*.py                  # présentateurs minces (ask_* / show_* uniquement)
gui/                           # futur, remplace/complète wui.py
  qt_ui_port.py                # implémentation Qt du même UIPort
  panels/*.py
services/api/...               # inchangé (déjà propre)
acquisition/, transformation/, persistence/  # inchangés
```

### 6. Ordre de migration suggéré

Je commencerais **par le pire cas**, `cli/layer5/etapes.py`, parce que c'est le plus couplé — si le contrat tient là, il tient partout ailleurs :

1. Extraire `Layer5Service` (scan / search / qualify / push) → retourne des dataclasses (`ScanResult`, etc.), zéro `console.*`.
2. Introduire `UIPort` + `RichUIPort`, réécrire `cli/menus/layer5.py` en présentateur pur.
3. Vérifier que le CLI actuel se comporte identiquement (non-régression).
4. Répliquer le pattern sur `organisation.py`, `entreprise.py`, `etablissement.py` (plus simples, surtout du CRUD).
5. Seulement à ce stade, attaquer `wui.py` : écrire `QtUIPort` et brancher les services existants dans les panels Qt.
