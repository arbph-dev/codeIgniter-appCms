# ORBIS — Backlog technique (migration Layer5Service, Phases 0-5)

Consolidé au fil des phases 0 à 5. Rien ici n'a été corrigé sauf mention
explicite « ✅ Corrigé » — la philosophie de la migration a été
équivalence stricte d'abord, corrections ensuite, pour ne jamais changer
deux choses à la fois (comportement + structure du code).

---

## P1 — Bugs de comportement à corriger

### 1. `WMRecord.Pythonlocal_id` — typo de champ
- **Fichier** : `cli/layer5/working_memory.py`
- **Constat** : le champ est déclaré `Pythonlocal_id` (ligne commentée
  `# 2026-08-31-004 - PK SQLAlchemy`) alors que tout le reste du code
  (`etapes.py`, `show_wm`, et maintenant `Layer5Service.persist_record`/
  `push_to_zealot`) lit/écrit `rec.local_id`.
- **Pourquoi ça ne plante pas** : `WMRecord` est un `@dataclass` non
  `slotted` — Python autorise l'ajout d'attributs arbitraires après
  construction. `rec.local_id = saved.id` crée donc un attribut
  d'instance jamais déclaré ; `Pythonlocal_id` reste pour sa part
  toujours `None`, mort.
- **Piège découvert en Phase 5** : tout code qui construirait
  `WMRecord(local_id=...)` **au constructeur** (plutôt que par
  assignation dynamique après coup) plante avec `TypeError`. Le code de
  production ne le fait jamais au constructeur, donc n'est pas affecté —
  mais c'est un piège pour du futur code (tests, scripts, présentateur Qt).
- **Fix proposé** : renommer `Pythonlocal_id` → `local_id`. Sans risque
  de migration DB : `WMRecord` n'est pas un modèle persisté, c'est un
  objet WorkingMemory en mémoire uniquement.
- **Effort** : S (renommage + grep de contrôle sur tout le repo)

### 2. Statut `"error"` toujours écrasé par `"searched"`
- **Fichier** : `cli/layer5/etapes.py::_run_etape2` (legacy) /
  `core/services/layer5_service.py::search_and_score` (reproduit à
  l'identique, volontairement, pour la Phase 3)
- **Constat** : si `insee_client.search_siren()` lève une exception,
  `rec.status` passe à `"error"`, puis est immédiatement écrasé par
  `"searched"` deux lignes plus bas. Le statut d'erreur ne survit donc
  jamais dans `WorkingMemory`.
- **Atténuation déjà en place** : le message d'erreur est désormais
  récupérable via `SearchOutcome.error` (n'existait pas avant — avant,
  le `console.print` de l'erreur était perdu une fois affiché).
- **Fix proposé** : ne pas réécraser `"error"` par `"searched"`, ou
  introduire un statut distinct (`"search_error"`) si on veut garder la
  trace dans `WorkingMemory` lui-même plutôt que seulement dans les
  outcomes retournés par l'appel.
- **Effort** : S

### 3. Fallback INSEE (tokens) non protégé par `try/except`
- **Fichier** : idem (etapes.py legacy / search_and_score reproduit)
- **Constat** : le premier appel `search_siren()` est protégé ; le
  second (fallback sans stop-words) ne l'est pas. Une exception à ce
  stade remonte jusqu'au handler générique de `main6_light.py`
  (`except Exception as e: console.print(...)`), qui abandonne le reste
  de la boucle sur les records suivants — pas seulement le record en
  cours.
- **Fix proposé** : wrapper le second appel dans un `try/except`
  identique au premier.
- **Effort** : S

### 4. Requête vide → record silencieusement absent du résumé
- **Fichier** : idem
- **Constat** : si `build_denomination_query()` renvoie une chaîne
  vide (nom composé uniquement de caractères combinants Unicode — cas
  extrêmement rare en pratique), le record est bien scoré (à vide) mais
  **aucune ligne n'apparaît** dans le résumé/la liste d'outcomes.
- **Fix proposé** : produire systématiquement un `SearchOutcome`, même
  vide, pour que chaque record scanné reste visible côté présentateur.
- **Effort** : S

## P2 — Dette technique / robustesse

### 6. `EntrepriseMapper.merge()` plante si appelé
- **Fichier** : `transformation/mapper.py`
- **Constat** : `merge()` (et donc `enrichFromInsee()` qui l'appelle)
  utilise `dataclasses.fields(EntrepriseModel)` — mais `EntrepriseModel`
  est une classe ORM SQLAlchemy déclarative, pas un `@dataclass`.
  `dataclasses.fields()` lèverait une `TypeError` si ces méthodes
  étaient un jour invoquées.
- **Pourquoi ce n'est pas bloquant aujourd'hui** : le chemin actuel
  (`reconcileZealot()`, utilisé par `persist_record`) n'appelle jamais
  `merge()`/`enrichFromInsee()`. Code mort tant que personne ne les
  invoque.
- **Fix proposé** : soit itérer sur `EntrepriseModel.__table__.columns`
  (comme le fait déjà `SirenGuard._force_update` pour un besoin
  similaire), soit migrer `EntrepriseModel` vers
  `MappedAsDataclass` (SQLAlchemy 2.0) si on veut vraiment le faire
  cohabiter avec `dataclasses.fields()`.
- **Effort** : S-M

### 7. Vérification SIREN check-then-act non atomique
- **Fichier** : `persistence/repository.py::EntrepriseRepository.create` /
  `persistence/siren_guard.py::SirenGuard.check_and_save`
- **Constat** : `persist_record` vérifie `repo.get_by_siren()` **avant**
  d'appeler `repo.create()`. Dans ce flux normal, la branche
  `except ConflictError` de `persist_record` est **du code mort** en
  usage séquentiel mono-utilisateur : `SirenGuard` (qui détecte
  vraiment le conflit *pendant* `create()`) n'est jamais atteint tant
  que la lecture préalable voit déjà l'existant. Le conflit ne peut
  survenir qu'en cas de lecture obsolète — typiquement une race
  condition entre deux utilisateurs/process concurrents traitant la
  même organisation en même temps.
- **Pourquoi c'est à surveiller, pas juste "pas grave"** : le CLI actuel
  est mono-utilisateur, donc sans risque réel aujourd'hui. Mais toute
  évolution vers une IHM multi-session (Qt/`wui.py`, ou plusieurs
  opérateurs en parallèle sur la couche 5) réintroduit un vrai risque de
  double-insertion SIREN si deux sessions traitent le même candidat au
  même instant, puisque le check applicatif (`get_by_siren` puis
  `create`) n'est pas transactionnellement atomique entre les deux
  appels.
- **Fix proposé** : s'appuyer sur la contrainte `UNIQUE(siren)` déjà
  présente en base et capturer `IntegrityError` directement dans
  `SirenGuard.check_and_save`, plutôt que de dépendre uniquement du
  check applicatif préalable — rendrait l'opération réellement atomique
  côté DB.
- **Effort** : M (implique de revoir la gestion d'erreur SQLAlchemy dans
  `SirenGuard`, et de re-tester le chemin conflit en conditions de
  concurrence réelle, pas seulement simulée comme en Phase 4)

## P3 — Amélioration produit

### 8. Filtre localisation au niveau de la requête INSEE (pas juste en scoring)
- **Fichiers concernés** : `core/services/layer5_service.py`
  (`build_denomination_query`, `search_and_score`, `_apply_loc_hint`)
- **Constat** : `loc_hint` (saisi à l'étape 2) ne sert aujourd'hui qu'à
  `score_loc()` en post-traitement — jamais à réduire la requête envoyée
  à INSEE en amont.
- **Cas réel observé en test manuel** : Gifi, Hénaff, Crédit Agricole —
  plusieurs candidats à égalité de score, aucun moyen de les distinguer
  sans une localisation exploitable dès la requête.
- **Piste technique** : l'API Sirene accepte de combiner des critères
  établissement dans la même requête `q=`, par exemple :
  `q=periode(denominationUniteLegale:"CREDIT AGRICOLE") AND periode(codePostalEtablissement:29*)`
  ou `AND departementEtablissement:29`. À implémenter via une fonction
  dédiée `build_location_filter(loc_hint)` concaténée avec `AND` à la
  requête de dénomination existante.
- **Effort** : M (nouvelle fonctionnalité, nécessite ses propres tests —
  pas de l'équivalence, du comportement neuf)
