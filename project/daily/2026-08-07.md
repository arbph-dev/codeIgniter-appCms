voietype_id — itemDisplay: (item) => item.nom après sélection dialog, displayFn: (data) => data.voietype_nom en mode fill(). Pas de required — le champ peut rester vide.

codepostal_id — itemDisplay joint codepostal + commune, displayFn joint cp_codepostal + cp_commune depuis les données JOIN de l'API. Ordre dans bootstrap() — les dialogs sont créés avant _createPanels(). C'est important : render() de RelationPickerDialog appelle dialogManager.register() qui insère le <dialog> dans document.body. Quand AdresseDetailPanel construit ensuite le formulaire via Form.js, les bus subscriptions dialog:select des champs relation sont déjà prêtes à recevoir.

render() est chaîné — new RelationPickerDialog({...}).render() retourne this, donc this._cpPicker reçoit bien l'instance, pas undefined.

destroy() dans l'ordre inverse — les dialogs se ferment avant les panels, ce qui évite qu'un dialog:select en transit trouve un Form déjà détruit.
