### 2. Processus couche 5 (générique, réutilisable)

La couche 5 n’est **pas** « du code entreprise ». C’est un **orchestrateur d’enrichissement** :

text

```
┌─────────────────────────────────────────────────────────────┐
│  COUCHE 5 — Qualification / enrichissement                  │
│                                                             │
│  1. SCAN      entités cibles incomplètes (règle métier)     │
│  2. ACQUIRE   sources externes (API référentiel)            │
│  3. SCORE     candidats vs jeu local (pondération champs) │
│  4. QUALIFY   choix humain (ou règle auto si score élevé) │
│  5. MAP       source → modèle cananique (couche 3)          │
│  6. PERSIST   base locale Orbis (couche 4)                  │
│  7. PUSH      API métier Zealot (couche 2 client)           │
│                                                             │
│  WorkingMemory = état de session (records + scores + ids)   │
└─────────────────────────────────────────────────────────────┘
```

**Invariant** : la couche 5 **n’appelle pas SQL ni HTTP métier en dur**. Elle enchaîne des ports déjà définis (clients, mapper, repository).

**Pattern pour une autre API** (personne, produit, événement, adresse…) :

|Étape générique|Entreprise (fait)|Ex. Personne|Ex. Adresse|
|---|---|---|---|
|Scan|org type=1 sans ligne entreprises|personnes sans date_naissance|adresses sans ban_id|
|Acquire|INSEE Sirene|(INSEE décès / autre)|BAN search|
|Score|nom, siren, naf…|nom+prénom+dates|label, score BAN, CP|
|Qualify|liste candidats / saisie SIREN|choix fiche|choix suggestion BAN|
|Map|reconcileZealot|PersonneMapper|AdresseMapper|
|Persist|EntrepriseRepository|PersonneRepository|local ou skip|
|Push|attach_to_organisation|PUT /personne|POST /adresse + lien|

Le **même squelette** (WorkingMemory + étapes numérotées + scoring pondéré + validation humaine) se duplique par domaine, pas par endpoint.

### 3. Audit du flux Entreprise actuel

text

```
[Zealot] org orpheline
    │  list type=1 + index entreprises (client)
    ▼
[WM] WMRecord (nom, siren?, zealot)
    │  Lucene periode(denomination…)
    ▼
[INSEE] unitesLegales → EntrepriseInsee[]
    │  score_nom / siren / naf / fj / etat → M% V% G%
    ▼
[User] choix # ou SIREN manuel
    │  reconcileZealot
    ▼
[Orbis DB] entreprises (siren unique, id_zealot)
    │  attach POST
    ▼
[Zealot] organisations.siren
         entreprises (naf, forme)
         etablissements is_siege (siret)
```

#### Points forts

- Séparation claire des couches
- Scoring explicite et traçable (detail par champ)
- Validation humaine avant écriture serveur
- Transaction métier côté PHP (org / ent / siège)
- Double vérité : Orbis local (workbench) + Zealot (prod API)

#### Limites / dettes

|#|Constat|Impact|
|---|---|---|
|A|Scan orphelines **côté client** (list org + list ent)|Coût API, fragile si volume|
|B|Score **sans localisation** ni adresse|M% bas, bruit (« action »)|
|C|Nom org non réécrit avec dénomination SIRENE|Écart affichage Zealot / INSEE|
|D|adresse_id toujours null|Pas de géocodage / lien BAN|
|E|Établissement seulement **siège** à l’attach|Pas de multi-établissements|
|F|Pas de re-push idempotent|2ᵉ attach → erreur « déjà une entreprise »|
|G|404 INSEE = 0 candidat|Personnes physiques / noms mal orthographiés|
|H|OrganisationZealot / EntrepriseZealot encore partiels côté repo|DTO vs payload withRelations|

### 4. Rôle d’**Adresse** pour optimiser la couche 5

L’adresse est un **discriminant fort** (avec le SIREN) :

text

```
Org (nom ambigu)
  + code postal / commune  →  requête INSEE ou filtre post-INSEE
  + BAN                    →  ban_id, score, coordonnées
  → score localisation (aujourd’hui stub ×4) devient réel
```

**Flux enrichi (cible)** :

text

```
Scan org
  → si adresse_id : charger Adresse Zealot
  → sinon : BAN(nom + indices texte)  [optionnel, bruyant]
  → INSEE (nom [+ filtre geo si dispo])
  → score : nom×4 + siren×8 + loc×4 + naf×2 …
  → qualify
  → persist local
  → attach (+ siret siège)
  → BAN reverse ou search sur siège INSEE (adresse établissement)
  → POST /adresse + lier etablissement.adresse_id (et optionnel org.adresse_id)
```

**Clients à poser** :

|Client|Responsabilité|
|---|---|
|AdresseClient (Zealot)|CRUD /adresse, lien org/établissement|
|BanClient (déjà)|search / reverse → AdresseBan|
|EtablissementClient (Zealot)|list by org, show, update adresse_id, hors siège|

Sans AdresseClient, la couche 5 s’arrête au SIRET ; avec, elle **ferme la boucle géo** et améliore le matching des pages suivantes.

### 5. EtablissementClient — pourquoi incontournable

Aujourd’hui le siège naît **dans** attach / ensureSiege. Ensuite :

- lire le siège sans recharger toute l’entreprise
- mettre à jour adresse_id, téléphone, email
- créer des établissements secondaires (GMAO, magasins)
- layer5 « établissements orphelins » (SIRET sans adresse)

Endpoints déjà esquissés côté PHP (byOrganisation, siege) : le client Orbis doit les exposer proprement.

### 8. Synthèse

La couche 5 est un **moteur de réconciliation** : scan → multi-sources → score → humain → map → local → push. Le cas Entreprise/SIRENE prouve le chemin jusqu’au siège SIRET sur Zealot.

Pour la suite, **Adresse** et **Établissement** ne sont pas de simples CRUD : ils :

- augmentent le **score** (localisation),
- complètent le **graphe** org → entreprise → siège → adresse,
- préparent d’autres domaines (GMAO, events, parcours).

Ordre de travail recommandé :

1. Documenter le process couche 5 (cette note) dans le repo
2. AdresseClient + mapping BAN → Zealot
3. Brancher localisation dans le scoring (étape 2)
4. EtablissementClient + étape 5 « lier adresse au siège »
5. Orphelines côté serveur + attach idempotent

Si tu veux enchaîner tout de suite, on peut commencer par le **squelette AdresseClient + AdresseZealot** calé sur ton AdresseModel / sample existant.
