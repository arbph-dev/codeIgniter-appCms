l’application peut évoluer sans abandonner panel-card et tab-content.
- conserver ces éléments comme structure éditoriale et navigationnelle
- intégrer les workbenches comme des composants fonctionnels à l’intérieur des panneaux.


Séparer clairement trois niveaux :

```
Application
├── Panel
│   ├── titre
│   ├── description
│   └── Sections / onglets
│       └── Workbench ou composant
```

```html

    data-panel="adresses"
>

        >
            <h3>Aide</h3>
            <p>Documentation de la recherche d'adresses.</p>
        </section>
    </div>
</div>
```

Le workbench ne devrait donc pas devenir lui-même un .panel-card.

Pourquoi conserver cette séparation ?
Le .panel-card représente actuellement une unité de contenu :

un titre ;
une description ;
une entrée dans la navigation ;
une position dans la pagination ;
éventuellement plusieurs onglets.
Le workbench représente autre chose :

une fonctionnalité interactive ;
son propre état ;
ses appels API ;
ses contrôles ;
éventuellement son cycle de vie init, mount, destroy.
Cette séparation est saine et correspond déjà à l’architecture décrite dans assets/ui_html.md et dans le prototype wbapp.js.

Faut-il revoir AdresseWorkbench ?
Oui, mais plutôt son intégration que son principe.

La structure actuelle :

```html
<div id="adresses-1" class="tab-content">
    <h3>Travaux en cours</h3>
    <div id="adresse-workbench" class="workbench" data-workbench="adresse"></div>
</div>
```html

Modifier :
- le nom de l'onglet ;
- le contenu temporaire Travaux en cours ;
- le cycle de vie du workbench ;
- le chargement différé lorsque l'onglet devient visible.

Par exemple :

```html
<div id="adresses-recherche" class="tab-content active" role="tabpanel">
    <h3>Recherche d'adresse</h3>
    <div
        id="adresse-workbench"
        class="workbench"
        data-workbench="adresse"
        data-lazy="true"
    ></div>
</div>
```html

Le composant pourrait ensuite être chargé uniquement lorsque cette section est activée.

chargement actuel des workbenches
- Le prototype de wbapp.js recherche tous les éléments [data-workbench] puis les monte immédiatement.

Cela fonctionnera pour un composant classique, mais cela peut poser problème pour :
- Leaflet dans un onglet caché ;
- des composants lourds ;
- plusieurs instances du même workbench ;
- des workbenches situés dans des panneaux non visibles ;
-des composants dépendants de l'authentification.


gestionnaire centralisé :

```js
const workbenchInstances = new Map()

async function mountWorkbench(element) {
    if (workbenchInstances.has(element.id)) {
        return workbenchInstances.get(element.id)
    }

    const type = element.dataset.workbench
    const module = await import(
        `/assets/js/ui/workbench/${type}/${capitalize(type)}Workbench.js`
    )

    const instance = new module.default()
    await instance.init(`#${element.id}`)

    workbenchInstances.set(element.id, instance)

    return instance
}

function destroyWorkbench(element) {
    const instance = workbenchInstances.get(element.id)

    if (!instance) return

    instance.destroy()
    workbenchInstances.delete(element.id)
}
```js
Puis, au changement d'onglet :

```js
function switchSection(index) {
    const panel = _main_panels[_currentPanel]
    const sections = qsa(".tab-content", panel)
    const buttons = qsa(".tab-btn", panel)

    sections.forEach((section, i) => {
        const active = i === index

        section.classList.toggle("active", active)
        section.hidden = !active
        buttons[i]?.classList.toggle("active", active)
        buttons[i]?.setAttribute("aria-selected", String(active))

        if (active) {
            const workbench = section.querySelector("[data-workbench]")

            if (workbench && workbench.dataset.lazy === "true") {
                mountWorkbench(workbench)
            }
        }
    })

    _currentSection = index
}
```
Cette approche est particulièrement importante pour les cartes Leaflet, qui doivent généralement être initialisées après que leur conteneur est devenu visible. Le code actuel appelle déjà initLeaflet(panel_Sections[index]), ce qui va dans la bonne direction.

Faire évoluer la gestion des panneaux
La logique actuelle repose principalement sur des index :

```js
function switchPanel(index) {
    _main_panels.forEach((panel, i) => {
        panel.classList.toggle("hidden", i !== index)
    })

    _currentPanel = index
}
```js
C'est simple, mais fragile. Une insertion ou une réorganisation des panneaux peut modifier tous les index.

Je recommande d'introduire des identifiants stables :

```html
<div id="panel-composants" class="panel-card" data-panel="composants" >
```
```
<div id="panel-m221" class="panel-card hidden" data-panel="m221">
```
Puis :

```js
function switchPanel(panelId) {
    const panels = qsa(".panel-card", _main)

    panels.forEach(panel => {
        const active = panel.dataset.panel === panelId

        panel.classList.toggle("hidden", !active)
        panel.hidden = !active
    })

    _currentPanel = panelId
}
```
La navigation pourrait générer des liens comme :

```html
<a href="#panel-adresses" data-panel-target="adresses">Adresses</a>
```
Cela rendrait également les URLs partageables :

```
/ui#panel-adresses
/ui#panel-adresses/adresses-recherche
```

Modèle d'état
Au lieu de stocker uniquement :

```js
_currentPanel = 5
_currentSection = 1
```
clé fonctionnelle :

```js
const uiState = {
    panel: "adresses",
    section: "recherche"
}
```

Le DOM pourrait ensuite être analysé pour construire les pages :

```js
function readPages() {
    return qsa(".panel-card", _main).map(panel => ({
        id: panel.dataset.panel,
        title: qs(".panel-title", panel)?.textContent.trim(),
        sections: qsa(".tab-content", panel).map(section => ({
            id: section.id,
            title: qs("h3", section)?.textContent.trim()
        }))
    }))
}
```
Cela conserve le principe actuel de readPage, mais remplace les positions implicites par des identifiants explicites.

Une évolution importante : les onglets ne doivent pas être obligatoires
Tous les panneaux ne contiennent pas nécessairement plusieurs sections. Il serait utile de supporter ces deux formes :

Panneau simple
```html
<div class="panel-card" data-panel="actualites">
    <h2 class="panel-title">Actualités</h2>

    <section class="panel-content">
        ...
    </section>
</div>
```
Panneau avec onglets
```html
<div class="panel-card" data-panel="adresses">
    <h2 class="panel-title">Adresses</h2>

    <div class="section-tab">
        <div class="tab-headers"></div>

        <section class="tab-content">
            ...
        </section>
    </div>
</div>
```
Le moteur de navigation doit donc détecter dynamiquement la présence de .section-tab, plutôt que de supposer que tous les panneaux ont des onglets.

Accessibilité à renforcer
L'interface actuelle gagnerait à utiliser les attributs ARIA :

```html
<div class="tab-headers" role="tablist">
    <button
        id="tab-adresses-recherche"
        class="tab-btn active"
        role="tab"
        aria-selected="true"
        aria-controls="adresses-recherche"
    >
        Recherche
    </button>
</div>

<section id="adresses-recherche" class="tab-content active" role="tabpanel" aria-labelledby="tab-adresses-recherche">
</section>
```
Il faudrait aussi :

utiliser hidden en complément de la classe CSS hidden ;
éviter les liens javascript:void(0) ;
utiliser des boutons pour les actions ;
gérer les touches Tab, ArrowLeft, ArrowRight, Home et End dans les onglets ;
synchroniser l'état avec aria-selected.
Organisation cible des responsabilités
Je viserais cette répartition :

```
uiapp.js
├── lecture du DOM
├── navigation entre panneaux
├── navigation entre onglets
├── pagination
├── état de l'interface
└── événements généraux
```
```
wbapp.js
├── découverte des workbenches
├── chargement dynamique
├── montage
├── destruction
└── gestion de l'authentification
```
```
AdresseWorkbench.js
├── rendu fonctionnel des adresses
├── recherche
├── résultats
├── carte
└── destruction de ses ressources
```
Ainsi, uiapp.js ne connaît pas le fonctionnement interne d'AdresseWorkbench. Il sait seulement qu'un workbench doit être monté lorsqu'une zone devient active.


Étape 1 — Stabiliser le modèle existant
- Conserver panel-card et tab-content.
- Ajouter id et data-panel à chaque panneau.
- Remplacer progressivement les dépendances aux index.
- Renommer les sections temporaires comme adresses-recherche.
- Ajouter hidden, role="tab" et role="tabpanel".

Étape 2 — Encapsuler le cycle de vie
- Ajouter init, mount et destroy aux workbenches.
- Éviter de monter immédiatement tous les workbenches cachés.
- Monter un workbench à l'ouverture de son onglet.
- Détruire ou suspendre les composants lourds si nécessaire.

Étape 3 — Ajouter une vraie gestion d'état
- Utiliser { panel, section }.
- Synchroniser cet état avec location.hash.
- Restaurer le dernier panneau consulté.
- Permettre l'ouverture directe d'une section.

Étape 4 — Généraliser le système de composants
- À terme, le DOM pourrait déclarer différents composants :

```HTML
<div data-component="adresse-workbench"></div>
<div data-component="leaflet-map"></div>
<div data-component="vox-player"></div>
```

Le système [data-workbench] est déjà suffisant pour stabiliser AdresseWorkbench.

## Conclusion
ne pas remplacerl'architecture actuelle. 
faire évoluer :
- panel-card reste l'unité de navigation et de contenu ;
- tab-content reste l'unité de section ;
- les workbenches restent des composants internes ;
- les panneaux utilisent des identifiants stables plutôt que des index ;

les workbenches sont montés à la demande ;
- uiapp.js gère la navigation ;
- wbapp.js gère le cycle de vie des composants.

Le principal travail consiste à supprimer son caractère provisoire, à mieux gérer le chargement différé et à rendre la navigation indépendante des positions numériques.
