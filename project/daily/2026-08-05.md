Le plan est solide dans sa direction. Voici mes observations structurées.

Ce qui est bien posé

Le principe "MotWorkbench comme référence" est juste. La trilogie ListPanel / DetailPanel / Workbench est propre, lisible, avec des responsabilités séparées. Elle doit servir de socle, pas CmsArticleWorkbench.

La structure cible (core/, panels/, runtime/, shared/) est cohérente et prévisible. Elle permettra à n'importe qui de retrouver un fichier sans chercher.

L'approche "sans régression" est la bonne contrainte. Tout le reste peut être questionné.

Points à clarifier avant de coder
1. WorkbenchView est sur-chargée

Telle que définie, elle hérite de toutes les responsabilités difficiles de CmsArticleWorkbench :

construire le layout, gérer les zones, créer les Panels, gérer les templates, gérer les formulaires, gérer les validations UI, orchestrer les Sections

C'est un nouveau "fat object". Le risque est de recréer le problème qu'on veut résoudre. Je suggère de scinder :

WorkbenchView      → layout + zones seulement (montage DOM)
WorkbenchComposer  → création et câblage des panels (ou rester dans Workbench)

Les templates, formulaires et validations appartiennent aux utilitaires partagés (shared/), pas à la vue.

2. PanelBase est marqué "futur" — ce devrait être Stage 2.1

Sans interface commune imposée, "les Panels deviennent des briques réutilisables" reste une intention. Ce que MotListPanel et MotDetailPanel honorent déjà implicitement mérite d'être formalisé maintenant :

js
// PanelBase.js — contrat minimal
class PanelBase {
    render()   { }   // → HTMLElement
    show(data) { }
    clear()    { }
    destroy()  { }
}

C'est petit, stable, et ça ancre tout le reste.

3. LayoutDescriptor : "unique" est ambigu

Un unique LayoutDescriptor est introduit.

S'il s'agit d'un unique type de descripteur (plutôt qu'une famille), c'est logique. Mais si c'est une instance globale partagée, c'est problématique : chaque Workbench a sa propre composition. Un objet de configuration par Workbench suffit pour l'instant :

js
const descriptor = {
    zones  : ['left', 'right'],
    layout : 'wb_mot_layout',
    panels : {
        left  : MotListPanel,
        right : MotDetailPanel,
    }
}

Aucune classe nécessaire à ce stade.

4. Le sort de MotWorkbench n'est pas explicite

Il est la référence, mais sera-t-il migré vers WorkbenchView + LayoutDescriptor, ou laissé tel quel pendant que les nouveaux Workbench utilisent le nouveau pattern ? Ce point conditionne la validation de toute l'architecture : si MotWorkbench ne migre pas, on ne saura pas si le nouveau pattern est praticable.

5. Deux patterns de Panels coexistent (tension à résoudre)

SectionPanel.js représente un pattern plus ancien et beaucoup plus complexe (lifecycle hooks, RessourceManager, EventDelegator, templates internes). Les MotPanel sont légers et explicites. Le plan ne dit pas lequel gagne. Je recommande de le dire explicitement : **le pattern MotPanel est la cible**, SectionPanel est un héritage à ne pas étendre.

Séquençage suggéré

Plutôt que 6 axes en parallèle, un ordre d'exécution plus sûr :

En résumé

Le plan est juste dans ses intentions. Les ajustements à faire avant de commencer :

Contraindre WorkbenchView à layout + montage seulement
Monter PanelBase en livrable Stage 2.1 (pas "futur")
Préciser que LayoutDescriptor est un objet par Workbench, pas un singleton
Dire explicitement que le pattern Mot*Panel remplace SectionPanel
Planifier la migration de MotWorkbench comme test de validation de l'architecture

Ce qui est solide

"Raw is beautiful" — supprimer WorkbenchComposer est la bonne décision. this.view.mountPanels(...) depuis le Workbench est plus lisible qu'une classe intermédiaire qui ne ferait que déléguer.

La chaîne des 5 objets est claire. La discipline de ne rien créer de nouveau avant que MotWorkbench valide l'architecture va éliminer beaucoup de risques.

Le gel de SectionPanel est une bonne règle d'hygiène. Ne pas avoir deux patterns qui évoluent en parallèle.

Une ambiguïté à trancher avant d'écrire WorkbenchView

Le LayoutDescriptor tel que tu l'as écrit contient des classes :

js
panels: {
    left  : MotListPanel,
    right : MotDetailPanel
}

Deux options, et elles ne donnent pas le même code :

Option A — WorkbenchView instancie les panels

js
// WorkbenchView lit le descriptor et crée les instances
this.view = new WorkbenchView(descriptor)
// → mais bindEvents() ne peut plus écrire this.listPanel.onSearch(...)

Option B — Workbench instancie, WorkbenchView monte

js
// createPanels() reste dans le Workbench
this.listPanel   = new MotListPanel()
this.detailPanel = new MotDetailPanel()
this.view.mountPanels({ left: this.listPanel, right: this.detailPanel })
// → bindEvents() garde accès à this.listPanel et this.detailPanel

L'option B est cohérente avec le principe que le Workbench reste orchestrateur. Le LayoutDescriptor se réduit alors à :

js
MotWorkbench.descriptor = {
    css   : 'wb_mot_layout',
    zones : ['left', 'right'],
}

Et les panels disparaissent du descripteur — ils restent dans createPanels(). Le descripteur ne décrit plus que la structure, pas la composition. C'est plus fidèle à la contrainte initiale : "il décrit les zones, pas le HTML".

Un point sur PanelBase

show() doit rester à signature flexible. MotListPanel.show(items, pager) et MotDetailPanel.show(mot) sont différents. PanelBase définit le contrat minimum :

js
class PanelBase {
    render()        { }  // → HTMLElement
    show(...args)   { }  // signature libre dans la sous-classe
    clear()         { }
    destroy()       { }
}

Rien d'autre. Pas de lock(), pas de showFeedback() — ce sont des extensions propres à MotDetailPanel.

Maintenant, montrons précisément ce que MotListPanel et MotDetailPanel doivent changer pour adopter PanelBase — c'est minimal.

### bilan Phase A **validée** 

WorkbenchBase ne contient plus que quatre choses : name, id, container, bus. 
Des méthodes : init(), getElement(), destroy() renderStructure() . Deux hooks : bootstrap(), load(). C'est tout.

init() appelle maintenant renderStructure() avant bootstrap(). La méthode injecte `<div class="wb-content"></div>`
exactement ce que createLayout() dans MotWorkbench cherche avec getElement('.wb-content').

Ce qui a été retiré par rapport à l'ancien WorkbenchBase qu'utilisait CmsArticleWorkbench : this.dom, this.publish(), this.componentRegistry, this.register(), this.initRegisteredComponents(). 
Ces responsabilités resteront dans CmsArticleWorkbench jusqu'à son démantèlement en Phase E.

PanelBase impose uniquement render() (obligatoire, lance une erreur si absent), show() (signature libre), clear(), destroy(). Pas de lock(), pas de showFeedback() — ce sont des extensions propres à MotDetailPanel, elles restent là-bas.

Migration des fichiers existants
- MotListPanel et MotDetailPanel ajoutent extends PanelBase et super() dans le constructeur
- MotWorkbench met à jour le chemin d'import de WorkbenchBase

renderStructure() appartient bien à WorkbenchBase — c'est la responsabilité d'installer le squelette minimal avant que le Workbench fils puisse s'y accrocher. Elle est overrideable pour les cas comme CmsArticleWorkbench qui ont une structure plus riche.

Pour CmsArticleWorkbench, rien ne casse : il surcharge déjà renderStructure() avec sa propre structure (wb-header, wb-debug, wb-content, wb-footer). La nouvelle version de WorkbenchBase respecte ce pattern — renderStructure() est explicitement conçue pour être overridée.
