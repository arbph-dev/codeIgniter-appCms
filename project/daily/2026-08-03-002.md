## Stage 2 - Consolidation
Contrats, Panels, CSS, Services homogènes

un Workbench devient un espace de travail, une View représente un mode de travail (catalogue, édition, aperçu, recherche...), et les Panels restent des briques d'affichage réutilisables.
### Workbench
Le Workbench ne met jamais directement l'interface à jour. Il met à jour son état, puis demande un rafraîchissement global de la vue (WorkbenchView).

Le Workbench reste focalisé sur l'évolution de l'état, pas sur les détails du rendu. Workbench fait simplement : refresh()
Puis le View décide :
- quels Panels mettre à jour ;
- dans quel ordre ;
- si un Panel doit être masqué ;
- si un autre doit être recréé.

```
Workbench
│
├── crée les Views
├── charge les Services
├── gère la navigation
└── partage l'état
```

#### Cycle de vie
```
constructor
────────────> Construction Aucun appel API. Aucun rendu métier. Uniquement la création des objets
bootstrap
createLayout
createWorkbenchView
createPanels
bindEvents
────────────> Initialisation À la fin, le Workbench existe visuellement mais ne contient encore aucune donnée.
load
refresh
────────────> Activation ouverture
user action
service
update state
refresh
────────────> Activation changement de contexte.
destroy
```

### WorkbenchView
```
WorkbenchView
│
├── crée les Panels
├── orchestre ses Panels
└── ne connaît pas l'API
```





```
Panel
│
├── construit son DOM
├── affiche
└── émet des callbacks
```

On obtient une hiérarchie très claire :
```
Workbench -> WorkbenchView -> Panel -> UI Components
```


cette hiérarchie est évolutive.





## Stage 3 - WorkbenchViews
Introduction du concept de WorkbenchView composé de Panels
Ajouter immédiatement une couche WorkbenchView reviendrait à déplacer des responsabilités avant même d'avoir plusieurs cas d'usage.






### etat actuel

Aujourd'hui un Workbench ressemble à cela :
```
Workbench
    ├── Panel
    ├── Panel
    └── Panel
```
Le ComponentCatalogWorkbench est encore simple :
- Catalog
- Definition
- Descriptor
- JSON

Une seule WorkbenchView suffit.

### évolution
Demain on devra produire des interfaces plus riches :
Workbench sera probablement composé de plusieurs WorkbenchView : Catalog, Explorer, Editor, Relations, History, Preview, JSON, Statistics

Le concept de WorkbenchView prendra tout son sens.
```
Workbench
    ├── WorkbenchView Catalog
    │      ├── CatalogPanel
    │      ├── DefinitionPanel
    │      └── JsonPanel
    │
    ├── WorkbenchView Search
    │      ├── SearchPanel
    │      └── ResultPanel
    │
    └── WorkbenchView Preview
           ├── PreviewPanel
           └── InspectorPanel
```

Autrement dit :
```
Workbench -> WorkbenchView -> Panel(s)
```


**Autre option**
```
Workbench -> ViewModel -> WorkbenchView
```

ViewModel introduit  un objet intermédiaire.

Workbench        │
        ▼
WorkbenchViewModel
        ├── layout
        ├── tabs
        ├── regions
        ├── panels
        └── data

Le Workbench construit ce modèle.
Le View ne fait que le rendre.
